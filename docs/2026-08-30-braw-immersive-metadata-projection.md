# BRAW Immersive Metadata → Equirect ("Use Metadata" projection source)

**Date:** 2026-08-30 · **Status:** IMPLEMENTED in v1.10.0 (same day) as projection mode
"Equirect (Camera Metadata)" — `src/BRAWLensMap.h` (parser + generator, unit-tested against
this doc's verified goldens), `src/BRAWImmersiveReader.cpp` (SDK extraction via the vendored
`third_party/braw/` dispatch shim), wiring in `src/NDIOutputPlugin.cpp`. Tier 1–2 pending.
**Sample media:** `B001_10151156_C001.braw` (URSA Cine Immersive, 8160×7200 per eye, 59.94, 455 frames)

## Question

URSA Cine Immersive BRAW clips carry factory lens calibration that Resolve/Apple
use to present the fisheye as immersive video without an external STMap. Can the
plugin read that metadata and warp to equirect itself — a "Use Metadata" option
next to the existing Equirect (STMap) mode?

**Answer: yes.** Every piece is verified end-to-end on the sample clip: the
metadata is readable in-process through Resolve's own Blackmagic RAW framework,
it fully describes both lenses, the projection model is confirmed numerically
and visually, and the output slots into the existing STMap pipeline as a second
map *source* with zero changes to the warp kernels.

## What the clip carries (verified by dump)

Blackmagic RAW SDK 5.0+ exposes `IBlackmagicRawClipImmersiveVideo` (QI from
`IBlackmagicRawClip`). On the sample clip:

| API | Value |
|---|---|
| `GetDistanceBetweenLenses` | 64000000 (nm → 64 mm) |
| `GetHorizontalFieldOfView` | 180000 (millideg → 180°, presentation FOV) |
| `GetComfortDisparityAdjustment` | 0 |
| attr `OpticalProjectionKind` | `fish` |
| attr `OpticalCalibrationType` | `meiRives` |
| attr `OpticalProjectionData` | 30 KB JSON (below) |
| attr `OpticalLensProcessingDataFileUUID` / `OpticalILPDFileName` | calibration UUID / `.ilpd` name |

The clip is dual-video-track (`IBlackmagicRawClipMultiVideo`, track 0 = left,
1 = right). General clip metadata confirms `camera_type = Blackmagic URSA Cine
Immersive`, `lens_type = Blackmagic 210º Fisheye`.

`OpticalProjectionData` is generated by the **Apple Immersive Camera Calibration
Service** (per-camera factory calibration). Per eye (`captureDevice.views[]`,
`viewDescription` left/right):

- **intrinsics** — model `radial2ProjectionOffsetTangential2`: `fx fy skew
  centerX centerY`, `distortions = [k1, k2, ξ, p1, p2]`,
  `calibrationLimitRadialAngle ≈ 109.59°`, `imageSize = [8160, 7200]`
- **extrinsics** — model `dualRectification`: unit quaternion (≈0.5° per eye)
  + translation (left `[0,0,0]`, right `[-64,0,0]` mm) — stereo rectification
  into a common rig frame whose baseline is purely x
- **maskData** — 64 control points, all unit vectors on a circle **80° off the
  optical axis**, `edgeWidth 2.5°`, `edgeTreatment linear` — the visionOS-style
  feathered circular porthole
- **opticalData** — measured FOV ≈ 203.66° × 188.88°

## The projection model (verified)

`meiRives` = Mei–Rives unified omnidirectional camera model. Camera frame is
CV-style **x right, y down, z forward**; for a unit direction `d = (x,y,z)`:

```
m  = (x/(z+ξ), y/(z+ξ))                      # sphere → normalized image plane
ρ² = mx²+my²;  L = 1 + k1·ρ² + k2·ρ⁴          # radial
xd = L·mx + 2p1·mx·my + p2(ρ²+2mx²)           # + tangential
yd = L·my + p1(ρ²+2my²) + 2p2·mx·my
u  = fx·xd + skew·yd + cx;   v = fy·yd + cy   # pixels in imageSize coords
```

Valid while `z+ξ > 0` and the radial angle `acos(z) ≤ calibrationLimitRadialAngle`.

**Numeric check:** a ray at half the stated horizontal FOV (203.66°/2 = 101.8°
off-axis) projects to 4085 px from center — the sensor half-width is 4080. Exact
agreement; confirms the model and the `[k1,k2,ξ,p1,p2]` ordering (ξ≈2.04 is the
third element).

**Visual check:** decoded frame 200 of both eye tracks via
`CreateJobImmersiveReadFrame` (quarter scale → 2720×2400) and warped to
1024×1024 equirect 180°×180° in Python. Clean equirect: straight architecture,
correct unwrap, content fills the frame including corners.

**Key geometric fact:** every direction inside a 180°×180° equirect is ≤ 90°
off-axis (boundary is exactly 90°), and the calibration is valid to 109.6° with
image-circle coverage to ~101.8° — so the metadata warp has real pixels for the
*entire* output frame. No black corners, unlike generic fisheye STMaps.

**Extrinsics convention:** treated as world(rig)-to-camera, `d_cam = R·d_rig`
(the CV standard). This is the only reading consistent with the right eye's
translation `(-64,0,0)` given x-right (rig origin = left eye sits 64 mm to the
right camera's left). Empirically the two candidate conventions differ by the
*difference* of the two eyes' quats — only ~0.04°, sub-pixel at any streaming
resolution; measured inter-eye vertical disparity is sub-pixel either way. If
ever proven wrong against a Vision Pro reference, the fix is one transpose.

**Equirect mapping (per eye):** map texel row r (top-down), column c, map size
W×H → `lon = ((c+0.5)/W − 0.5)·180°` (+right), `lat = (0.5 − (r+0.5)/H)·180°`
(+up); `d_rig = (cos·sin lon, −sin lat, cos·cos lon)`; rotate by the eye's R;
project; then STMap-normalize `u_st = (u+0.5)/8160`, `v_st = 1 − (v+0.5)/7200`
(STMap v is bottom-left origin; calibration v is top-down). Out-of-validity →
NaN texel (existing "outside the lens" behavior).

**maskData decode:** control points live in a y-up/z-*backward* frame (visionOS
convention; camera → mask space is a 180° flip about x). All 64 points sit
exactly 80° off-axis: a plain circle, feathered linearly over 2.5°. It exists to
hide the lens-edge smear; Apple players show this porthole.

## Runtime access from inside the OFX plugin

- Resolve ships `BlackmagicRawAPI.framework` **5.1 (50100.40.160)** in
  `DaVinci Resolve.app/Contents/Frameworks` — byte-identical version to the
  installed SDK's. The plugin runs inside Resolve's process.
- The SDK's BSD-licensed dispatch shim (`Mac/Include/BlackmagicRawAPIDispatch.cpp`,
  compiled into the plugin) resolves the API at runtime via
  `CFBundleGetMainBundle()` → `Contents/Frameworks` — i.e. **inside Resolve it
  finds Resolve's own framework automatically** (`CreateBlackmagicRawFactoryInstance()`).
  Nothing to ship, no linking, no version skew possible. Fallbacks (exe-relative,
  explicit path to the SDK install) exist for the standalone unit-test binary.
- Metadata-only access: `OpenClip` + `GetImmersiveAttribute` parses headers only
  — instant even on this 6.7 GB clip, no frame decode, no GPU use. Same
  call-site budget as the existing multi-hundred-MB EXR loads in
  `refreshSTMaps()` (createInstance/instanceChanged, never render).
- SDK license permits use/derivative works; the shim is sample code under a
  BSD-style grant. We redistribute no Blackmagic binaries.

## Design: metadata as a second map *source*

The insight that keeps this small: `StmapEntry`/`STMapImage` already define the
whole downstream contract (validation → Metal upload cache → per-eye render
selection → warp → pack). Camera metadata is just another way to *fill* those
structs.

New module `src/BRAWLensMap.h/.cpp` (+ the SDK dispatch shim), two functions:

1. `brawReadImmersiveCalibration(path)` → the `OpticalProjectionData` JSON
   string + the scalar attrs (BRAW SDK involved; macOS `.mm`-adjacent but pure
   C++/CF). Fails soft with an error string on non-immersive clips.
2. `generateLensMaps(json, outSize, maskMode)` → per-eye `STMapImage` (+ error
   string). **No SDK/OFX/Metal dependency — unit-testable**, same philosophy as
   `STMap.h`. Includes a minimal fixed-schema JSON extractor in the spirit of
   the minimal EXR reader (no third-party JSON dep), rejecting unknown
   `intrinsics.model` / `OpticalCalibrationType` values soft.

Plugin wiring (all mirroring existing STMap patterns):

- `kParamProjection` gains choice 2: **"Equirect (Camera Metadata)"**.
- New string param `brawClipPath` + native Browse button (`mac_open_file_dialog`
  with extension `braw`) in the projection group. Any clip from the same camera
  works — calibration is per-camera, not per-shot — so one pick covers a whole
  timeline shot on one rig.
- New choice `metadataMapSize`: 1024 / **2048 (default)** / 4096 square per eye
  (output equirect size; the existing Resolution divisor still applies on top).
  Generation cost ~8.4 M texels at 2048: sub-second on the refresh path.
- New choice `metadataMask`: **Off (default)** / Camera. v1 "Camera" = hard
  circle at 80° + edge (texels beyond → NaN; zero pipeline changes, the
  supersampled warp gives ~1-texel AA). The true 2.5° linear feather needs a
  per-texel weight multiplied into the warp — a small optional third channel /
  side buffer through CPU+Metal paths — noted as the one follow-up that touches
  kernels; defer unless the hard edge bothers anyone on the Quest.
- `refreshSTMaps()` grows a branch: projectionMode 2 →
  `brawAcquirePair(path, size, mask)` caching in `gStmapCache` under a decorated
  key (`braw:<path>#<size>#<mask>`), stat-keyed on the `.braw` like STMap
  entries. Both eyes generate together (one JSON parse); mono timelines use the
  left map exactly as today; `kProjActive`/`kProjError` statuses and Stream
  Status messaging unchanged.
- Render path, Metal upload, stereo pairing, packing: **untouched.**

Makefile: add `src/BRAWLensMap.cpp` + shim to SOURCES, `-I` the SDK Include dir
(headers checked into the SDK install; consider vendoring the two headers +
shim under `third_party/braw/` so builds don't require the SDK installed —
they're the redistributable sample-code parts). New `make test-brawmap` target;
fixture = the sample clip's calibration JSON checked into `tests/fixtures/`
(factory calibration of our own camera; 30 KB).

Unit tests (`tests/test_brawmap.cpp`):
- fixture JSON → maps generate; known angles land at known pixels (the 101.8° →
  4085 px identity above, center → (cx,cy), 90°-off-axis edge cases)
- STMap conventions: v flip, NaN outside validity, mask circle radius
- hostile/truncated JSON fails soft with error strings

## Testing loop (LEARNINGS §2)

- Tier 0: `make dev` + unit tests.
- Tier 1–2: install, restart Resolve, immersive timeline with the sample braw,
  Projection = Equirect (Camera Metadata), verify in NDI Video Monitor / Quest
  180 player: correct unwrap both eyes, stereo comfortable (rectification), and
  A/B against the current STMap workflow for parity. Playback started by a
  human, as always.
- Cross-check (optional Tier 2+): compare a still against Resolve's own
  immersive/equirect interpretation or Vision Pro playback to confirm the
  extrinsics convention choice.

## Costs, risks, open questions

- **Frames from Resolve are the raw fisheye** — already true today (the current
  STMap workflow on these clips depends on it). Timeline must remain 1:1
  full-frame (8160×7200-aspect), same caveat as STMap mode.
- `crop_origin (24,12)` in clip metadata is the sensor readout offset; the
  calibration is authored in *recorded-frame* coords (`imageSize` matches,
  center ≈ frame center) — ignore it.
- Extrinsics convention: chosen analytically; worst-case error if wrong is a
  ~1° global pointing shift and ~0.04° inter-eye — visually verified sub-pixel
  on real frames. Flag for the Vision Pro cross-check.
- Non-immersive braw / other cameras: `QueryInterface` fails or attrs missing →
  soft error → passthrough + status message, mirroring bad-STMap behavior.
- Windows/CUDA port: the Win SDK has the same dispatch mechanism
  (`BlackmagicRawAPIDispatch.cpp` + DLL); gate the feature `__APPLE__` for now
  alongside everything else GPU-side.
- Future: auto-pick the braw from the current timeline clip via Resolve's
  in-process scripting (fusionscript) — deliberately out of scope for v1
  (playhead↔clip mapping per frame is fragile; per-camera calibration makes the
  manual pick a one-time act per project).
- Future: feathered mask (weight channel through both warp paths); optional use
  of `GetComfortDisparityAdjustment`; `.ilpd`/JSON sidecar as an alternative
  input for clips whose braw isn't handy.
